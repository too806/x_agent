## 0. 这份文档是怎么来的（请先读这一段）

**方法：静态走查 —— 逐文件读代码 + 对照后端契约 + 核查库里现有数据。**
**不是**点击走查。

这么说的原因是这个阶段有一条硬约束（见 4b.1 需求第九、十四节）：

- 不为验证而**新建 Run**（会真实调用 X 与 LLM，消耗额度并污染数据）；
- 不为验证发布而**额外制造公开帖子**；
- 不**故意制造 `publish_unknown`**。

所以下面的结论来自"这一段代码会渲染成什么"+ "库里现在这批数据点下去会看到什么"，
而不是"我点了一遍"。**实地点击验收由你完成**（`http://127.0.0.1:5173`，
路径 A：新建 Run → 待审核 → 查看研究 / 草稿 / 规则检查 → 编辑 → 保存 → 检查审核记录；
路径 B：Reject → 输入原因 → 检查状态；外加打开一条已有已发布 Run 看发布内容与 X Post ID）。

走查中确实核对过的**数据**：`draft.status` 全库只有 `draft` 一个值（5 行）、
`review.status` 现值 `approve`（3 行）、`agent_run.status` 分布
（failed 3 / published 2 / completed 1 / approved 1 / waiting_for_review 1）、
`published_post.status` 现值 `published`（2 行）。

## A. 必须修

不解决就不能算完成。每条标注当前状态。

### A-1 ✅ 已修：筛选下拉里是原始英文枚举

运行记录页的"运行状态"下拉原先直接渲染后端枚举（`waiting_for_review`），发布记录页同理。
现在**显示中文、值仍是后端枚举**（发出去的是 `status=running`，不是 `status=运行中`）。
`<option value>` 保持英文是这个系统"后端状态值一个都不改"的必然结果。

### A-2 ✅ 已修：错误提示里的英文

后端 `detail` 是英文，而且**没有任何测试断言它们**（已核对 `tests/`）。
会真的撞上的是这两条，都不是理论错误 —— 另一个标签页、或同一个人点两次就会遇到：

| 后端原文 | 触发场景 | 界面上现在显示 |
|---|---|---|
| `run is not waiting for review (status=approved)` | 这个 Run 已被别处决定 | 这个 Run 已经不在等待审核了（当前状态：**已批准**）。 |
| `run review was already submitted` | 并发提交只有一个成功 | 这个 Run 的审核已经由别处提交过了。 |
| `run not found` | 打开了已不存在的 Run | 找不到这个 Run。 |

做法是**前端加对照表**（`utils/format.ts` 的 `backendErrorLabel`），**后端一个字节没改**。
认不出的错误**原样显示**，不兜底成"发生了未知错误"——那会把后端真正说的话盖掉。
后端原文以小字留在中文下面，理由是**排查时对得上服务端日志**。

> 更彻底的做法是把 `app/main.py` 里那 5 处 `detail` 改成中文。**本阶段没做**：
> 那是在一个"后端核心业务一行未改"的阶段里改 API 的对外文案，而且 `detail` 是给
> 所有调用方看的，不只是这个控制台。留给你决定。

### A-3 ✅ 已修：Analytics 三段口径说明是英文

`PUBLISH_OUTCOME_NOTE` / `DURATION_UNAVAILABLE_REASON` / `X_PERFORMANCE_UNAVAILABLE_REASON`
是后端下发的英文常量，**被 `tests/test_admin_api.py` 的三条断言锁着**
（`assert "per Run" in ...` 等）。改后端就要改测试，改测试又违背"UI 改动不能破坏后端测试"。

处理：后端常量原样保留，**前端按同一语义用中文重写**同一段口径。
代价如实记在 handoff 的 D7-old：同一套口径现在有两份表述，改口径要改两处。

### A-4 ✅ 已修：审核成功后只有一句通用提示

原先无论批准 / 编辑 / 拒绝，成功后都是同一句。三条路径的人想知道的事不一样：

| 动作 | 提示 |
|---|---|
| 批准 | 已批准，该内容可以进入发布流程。 |
| 编辑 | **编辑已保存**，该内容可以进入发布流程。 |
| 拒绝 | 已拒绝，**该内容不会进入发布流程**。 |

这不是文案讲究：按下"编辑"的人唯一想确认的是**改稿有没有存下来**，
按下"拒绝"的人唯一想确认的是**这条还会不会发出去**。

### A-5 ✅ 已修：拒绝理由没填时按钮是禁用的

禁用按钮只会让人盯着它猜"为什么点不动"。现在按钮**可点**，点了就提示
**"请输入拒绝原因"**，并随输入实时消失。

### A-6 ✅ 已修：发布确认没有点明"公开帖子"

按需求逐字写入，**不要为了界面简洁压掉任何一句**：

- 确定要发布到真实 X 账号吗？
- **该操作会创建一条公开帖子。**
- 它会立刻生效，并且无法从这个控制台撤销（要撤回只能去 X 上手动删除，而本系统不会跟着同步）。

勾选框：*我明白：这一下会立刻在 X 上公开发出这条帖子。*

### A-7 ✅ 已修：`publish_unknown` 缺少关键那句话

现在显式写出：**"系统无法确认 X 是否已经创建帖子。自动重试可能导致重复发布。"**
外加"在人来裁决之前，系统不会为这个 Run 自动再调一次 X"。
两个动作按需求命名：**标记为已发布** / **确认可能重复后重试**。

这条是整份走查里最不肯让步的一处：`publish_unknown` 与"发布失败"在数据结构上都叫
非终态之外的异常，但前者意味着**X 上可能已经有一条人人可见的帖子**。把它折叠成
普通失败，操作者就会顺手重发，然后得到两条帖子。

### A-8 ✅ 已修：抽屉里写操作成功后，背后的表格是旧的

在发布记录页点"查看运行"打开抽屉、在里面重发或裁决成功，**抽屉背后的那一行不会更新**。
抽屉自己不知道列表的存在，所以给它加了可选的 `onSettled`，由持有列表的页面传入自己的
`reload`。运行记录页同样接上（在抽屉里发布成功后，那一行的运行状态同样会过期）。

### A-9 ✅ 已修：`app/models/review.py:21` 注释与实现不符

注释写 `pending（待审）→ approved / edited / rejected`，实现写入的是**动作**
`approve` / `edit` / `reject`（`app/schemas.py:178` 的 `REVIEW_ACTION_STATUS` 是
动作→状态的映射表）。**只改注释，未动语义。**

### A-10 ⚠️ 待你裁决：表格列名与规格不一致（我按事实改了）

规格第六节写的是 `主题/运行状态/审核状态/发布状态/创建时间/更新时间`。
我用了 **`完成时间`** 而不是 `更新时间`，因为那一列绑定的是 `finished_at` ——
**未到终态的 Run 该字段为空**（库里就有 3 个 `failed` 之外的非终态 Run 没有这个值）。
把它叫"更新时间"是错的：它不随更新变化。

若你要的就是字面上的"更新时间"，那需要改的是**字段来源**（换成 `updated_at`）而不是
列名 —— 说一声我就改。

### A-11 ⚠️ 待你裁决：侧栏两处英文

| 位置 | 文本 | 我的判断 |
|---|---|---|
| 侧栏品牌名 | `X AI Content Agent` | 是产品名，建议保留 |
| 侧栏页脚 | `Phase 4b` | 是阶段标识，可改成"阶段 4b" |

**全站扫描确认：除这两处，界面正文没有任何渲染出来的英文**
（`X` / `API` / `Post ID` / `Run ID` / `HTTP` / `outcome` / `checkpoint` / `LangGraph`
与 `<code>` 内容按规格保留）。扫描同时确认：没有 `**` 被当字面星号渲染，
没有残留的占位符碎片。

### A-12 ⚠️ 验收前置（操作项，非产品缺陷）

**`127.0.0.1:5173` 目前服务的是主检出，标题仍是 `X AI Content Agent · Operations Console`
（英文旧界面）。** 中文化代码在工作树里。开始验收前必须让 5173 指到新代码，
否则你会对着旧界面做验收。见本文末尾"如何开始验收"。

## B. 可以优化

不影响正确性，但用起来会硌一下。**本阶段都未修**（按"测试过程中不要随手改所有问题"）。

| # | 问题 | 说明 |
|---|---|---|
| B-1 | **发布记录表信息密度偏高** | 现在 9 列，操作列里叠了最多 4 个元素（查看运行 / 在 X 中打开 / 重发 / "需要在下方裁决"）。这是 A-8 加"查看运行"和 `创建时间` 列之后的代价。真要减，得砍列或把操作收进一个菜单。 |
| B-2 | **研究内容顺序不稳定** | 后端 `ORDER BY created_at, id`，而同一事务插入的行 `created_at` 完全相同、`id` 是随机 uuid4 → 两次打开同一个 Run，研究条目顺序可能不同。只影响展示，不影响内容；改它要动后端查询（属 Research 相关，不在本阶段范围）。 |
| B-3 | **编辑模式没有 diff 高亮** | 现在的做法是"原始内容"整块在编辑框上方，人得自己对。对长稿不够友好。 |
| B-4 | **连续决策没有快捷键** | 审核工作台的设计前提是"连续决策"，但每条都要用鼠标点按钮。键盘流（批准=1、编辑=2、拒绝=3）会让核心路径快很多。 |
| B-5 | **相对时间会随渲染漂移** | "3 分钟前"只在渲染那一刻算一次；`title` 里有绝对时间，但表格里显示的那句话可能已经过期（页面不会自己重算）。 |
| B-6 | **Analytics 同时存在两种口径** | 两张图按窗口、四块按全库。每块都标了范围（这是 4b 就定下的做法），但整个页面上"窗口"这个控件只影响一半内容，第一眼仍然容易误读。 |
| B-7 | **总览队列各只预览 10 条** | `OVERVIEW_QUEUE_PREVIEW = 10`。超过 10 条时显示"查看全部 N 条 →"。数据量大时首页看不到全貌。 |
| B-8 | **待裁决队列不主动提醒** | 4a 遗留：`publishing` / `publish_unknown` 挂着不会通知任何人，只有打开控制台才看得到。侧栏给了计数和红色标记，但仍是被动的。 |

## C. 当前可接受

刻意如此的设计，或者已经靠文案把话说清楚了。列在这里是为了**说明它们不是漏项**。

| # | 项 | 为什么可接受 |
|---|---|---|
| C-1 | 编辑计数按后端 `len()` 口径，**不是** X 加权字数 | 已明确标注「字数按本系统的口径统计（后端 `len()`），**不是** X 的加权字数」。这个数字的用途是**如实预告后端会不会打回**，所以它就该用后端那套口径。 |
| C-2 | KPI 是全量、趋势图是窗口内 | 已分块标注（"全量计数，不受上方窗口限制" / "最近 N 天 · 按 UTC 自然日"）。混成一个标题才会骗人。 |
| C-3 | 发布状态显示 `—` | 表示**没有发布记录**，不等于"还没发"，也不允许用 Run 状态顶替。 |
| C-4 | 审核决策分布里有"其他"桶 | 为了四项之和恒等于审核记录总数。吃掉未知状态比丢掉它们诚实。 |
| C-5 | 没有删除按钮，也没有"标记删除" | 审计记录语义。在 X 上删了推文，本地行不变，**也不该变**。 |
| C-6 | 没有 X 内容指标（曝光/点赞/互动率） | 显示"暂未接入 X 内容指标同步"，**不显示 0**。"0 曝光"会被读成"没人看"，而事实是"我们不知道"。 |
| C-7 | 规则检查读不到时显示 `—` | 不用数据库里的近似值顶替 checkpoint 的真实结果；配文明确"这**不等于**通过"。 |
| C-8 | 四个发布状态没有被合并 | 拒绝把 `publish_unknown` 折叠进 `failed`（见 A-7）。 |
| C-9 | 没有 WebSocket / SSE | 本阶段非目标；写操作后自动重取当前视图，其余靠"刷新"。 |
| C-10 | 前端没有测试框架 | 验证手段是 `tsc --noEmit` + `vite build` + 人工验收（见 handoff 第 7 节）。 |
| C-11 | 总览有 6 个 KPI，规格列了 5 个 | 多出来的是"发布中"（4b 就有的卡片，本阶段只是翻译）。它和"发布结果未知"是两种不同的未定状态，合成一个会丢掉"已发起、结果未记录"这层信息。若你要严格的 5 个，说一声就删。 |
| C-12 | 放弃引入 i18n 框架 | 单一语言、单一词典文件（`utils/format.ts`）。这个规模上 `react-i18next` 只是多一层间接。 |

## 九个重点检查项的结论

| 检查项 | 结论 |
|---|---|
| **Review 字段语义** | 材料按"题目 → 研究内容 → AI 生成草稿 → 规则检查 → 人工决定"排列，与决策所需的顺序一致。规则检查**排在草稿之后**是有意的：先让人自己读完，再看机器意见，否则容易变成对着结论点头。 |
| **Edit 的自然性** | 显示"原始内容 / 编辑后的内容 / `93 / 140 字`"，超限时计数变红且提交按钮禁用。计数口径已注明不是 X 加权字数。缺 diff 高亮（B-3）。 |
| **Reject 的清晰度** | 理由必填、未填有明确提示；提交按钮写明"拒绝这份草稿"；下方一句"拒绝会结束这个 Run。不会有任何内容发到 X。"成功提示见 A-4。 |
| **发布确认的清晰度** | 见 A-6。二次确认 + 勾选 + 三句指定文案，**没有削弱**。 |
| **`publish_unknown` 的可理解性** | 见 A-7。状态名是"发布结果未知"，配文说清"X 上可能已经有帖子"，两个动作按需求命名，并明确"自动重试可能导致重复发布"。 |
| **Dashboard KPI 清晰度** | 后四项取自发布记录而非 Run 状态，页面底部专门写了这句；KPI 全量与趋势窗口的分歧已标注。 |
| **Analytics 的可信度** | 算不出的标"暂不可用"并说明缺什么、为什么缺（不返回 0）；per Run vs per attempt、窗口内 vs 全库都写在各自的块上。 |
| **中文措辞一致性** | 状态词全部出自 `utils/format.ts` 的四张映射表，约 20 处徽标共用一个词典 → 同一个状态不可能出现两种译法。`失败`/`发布失败` 的分歧是有意的（同名不同义）。 |
| **信息密度** | 发布记录页偏密（B-1），其余四页可接受。 |

## 如何开始验收

**前置：让 5173 指向新代码。** 当前 5173 上跑的是主检出的旧（英文）界面。
在**主检出** `E:\2026_agent\X_Agent` 里执行（工作树分支已提交）：

```bash
git merge worktree-phase-4b1-i18n     # fast-forward，不会产生 merge commit
```

现有的 Vite dev server 会热更新，页面标题应变成
`X AI Content Agent · 运营控制台`，界面即为中文。**不需要重启前端。**

后端如果没在跑，按 handoff 第 9 节启动（**必须带 `HTTPS_PROXY`**，否则发布路径
访问不到 x.com）。

**然后**按 4b.1 需求第九节的两条路径验收。验收时若发现 A/B 分类不准，或 C 类里
有你不接受的，直接说 —— 这份文档的分类是走查得出的判断，不是结论。
