# 前端产品化 —— Phase 4b.2 记录

**范围**：只动 `frontend/**`。没有新增依赖、没有新增后端 API、没有改 API 契约、
没有改业务语义、没有碰 Agent / Publish / Review / 数据库 / migration。

**目标**：把 `http://127.0.0.1:5173` 从"渲染 API 数据的 React 演示"变成"一个真正的
AI Agent 内容运营控制台"。

**一句话结论**：控制台的**信息架构**从"每个后端字段一节"改成了"人要做的判断一层"；
**视觉系统**收到了同一套 token 与刻度上；**Agent 决策轨迹**被提到了详情里最好的位置；
**发布风险**（尤其是"结果未知"）在界面上有了独立的、不易误读的形态。

分层规矩（本次明确下来的）：

- **状态英文枚举只活在后端和 `utils/format.ts` 的映射表里**，界面上一律中文。
  认不出的枚举**原样显示英文**，不塌成"未知"——缺口要看得见。
- **`agent_run.status` 与 `published_post.status` 是两个权威**，各自一套文案
  （`failed` → 运行状态"失败" / 发布状态"发布失败"），页面上分开呈现。
- **空值一律 `—`**（`format.ts` 的 `EMPTY`），从不显示 `null` / `undefined` / `NaN`，
  也不用邻近字段猜一个默认值。

## 2. 改动前的"演示感"来自哪里

按影响从大到小：

1. **信息架构是"字段驱动"的。** 数据分析页七个平级 section、其中四个各装一张卡；
   Run 详情先铺研究素材、把结论压在最后。读者没有层级可循，只能从头读到尾。
2. **同一个动作在不同页面长得不一样。** 审核页自己长一条绿色横条提示成功，发布页
   是另一套；"加载中…"是纯文字，数据到达后页面跳一下。
3. **状态只靠颜色。** 表格里的错误是一个纯色小圆点，含义只存在于 `title` 里。
4. **长文本没有收口。** 正文、错误、主题都可能把表格行高撑垮；UUID 完整铺开会挤掉
   相邻列。
5. **技术字段直接铺在界面上。** `agent_decision` 表整行铺开就是一坨 JSON。
6. **空/错状态缺失或敷衍。** 有几处只写"暂无数据"，不区分"从来没发生过"和
   "筛选条件没匹配上"；错误直接吃后端的原始响应。
7. **间距/字号靠手写数值。** 13px、10px、9px 散落在各处，没有刻度。
8. **导航项在窄屏只剩图标、没有名字**（`display: none` 连无障碍树一起摘掉了）。

## 4. Agent 决策轨迹（§11）

这是整个控制台里最能说明"这是一个 Agent"的地方，所以给了它最好的位置和排版。

**位置**：详情里的第三段 —— 状态条 → 生命周期 → **Agent 决策轨迹** → 运行质量 →
研究素材 / 内容 / 规则检查 / 发布 → 运行信息。排在所有材料之前。

**每一步显示什么**（`components/ui/TraceTimeline.tsx`）：

- 左侧序号节点（顺序本身就是信息），按动作类别着色（研究蓝 / 生成紫 / 评审黄 / 改写 /
  收尾），**认不出的动作落到中性灰但照样显示，绝不隐藏**；
- **动作中文名**（`format.ts` 的映射表，取值与 `app/agent/schemas.py::AgentAction` 一一对应）：

  | 后端枚举 | 界面文案 |
  |---|---|
  | `discover_topics` | 发现候选 |
  | `research_topic` | 研究主题 |
  | `deepen_research` | 深入研究 |
  | `extract_evidence` | 提炼证据 |
  | `generate_angles` | 生成观点角度 |
  | `select_angle` | 选择观点角度 |
  | `generate_candidates` | 生成候选 |
  | `criticize` | 内容评估 |
  | `revise` | 修改内容 |
  | `finish` | 完成 |

- **理由**（`reason`）：唯一由 Agent 自己写、也是唯一回答"为什么"的字段，给正文的
  字号和行高。空理由说成一句"这一步没有留下理由。"——留白看起来像渲染出错；
- **摘要**（`result_summary`）与**作用于**（`target`）：默认可见。轨迹只有动机没有
  结果的话，读起来像一段心里活动而不是一次工作过程；
- **时间**：绝对时间；序号在节点上，所以不再重复"第 N 步"（读屏用户需要，
  放在 `.sr-only` 里）；
- **技术细节**（后端枚举值、输入摘要）折进 `<details>`：默认展开会把上面几层淹掉。

区块标题右侧给一行概览（`utils/trace.ts::traceSummary`）："9 步"，步号不连续时
说"第 1–3 步，共 2 条"——中间缺的那一步是有信息量的。

## 5. 需要说明的几个判断

这几处是有意偏离"最直白的做法"的，写在这里以便复核。

1. **发布 / 裁决的结果用页内常驻提示，不用 Toast。**
   Toast 用于"操作成功且界面会离开当前位置"（审核决定，随后跳到下一条）和复制确认。
   发布的结果**必须留在原地**：它带着 X Post ID、时间、`outcome` 枚举值，是事后对账
   的唯一凭据；一个会自动消失的浮层承受不了这个。`ui/Toast.tsx` 里原本就写着这条
   原则（"关键结论不能只住在 toast 里"），这里是把它执行到底。

2. **计数型的 0 照常显示，不算"没有数据"。**
   窗口内 Run 数 = 0 是一个**真实测量值**（这个窗口里确实一条都没有），把它换成
   "暂无足够数据"反而是在说"算不出来"。所以计数照显示，但用 `kpi--quiet` 压暗。
   真正算不出来的（平均运行时长样本为空）才显示"暂无足够数据"，并说明缺的是哪一类
   Run。分布与趋势在无数据时一律走空态文案，不画零长度的条。

3. **裁决不做成二级菜单。**
   "标记为已发布 / 确认可能重复后重试"两个按钮直接摆出来。多一层点击只会让人机械地
   点下去，而这两个动作恰恰需要人想清楚。真正不可逆的那一步（重试确认框，两个勾选）
   才是该减速的地方。

4. **发布记录页没有删除，也没有"标记已删除"。**
   这是审计记录，不是 X 的实时镜像。在 X 上删掉帖子，这里不该跟着变。页面上明说这一点。

5. **`goal` 不当作 `topic` 显示。**
   Agent 模式（Phase 5A）的 Run 在选出主题前 `topic` 是 null。此时列表显示
   `目标：<goal>`（带前缀、看得出这是输入不是结论），而不是把 goal 冒充成题目——
   一个还在选题的 Run 和一个已定题的 Run 长得一样，比空白更糟。

6. **数据页的"暂无足够数据"与"暂未接入 X 内容指标同步"是两种不同的缺失。**
   前者是"有这类数据但现在样本不够"（平均运行时长），后者是"这些数据从来没有被采集过"
   （曝光 / 点赞 / 转发 / 收藏 / 互动率）。两者文案、位置、后续动作都不同。

## 6. 已知未做 / 遗留

### P1 遗留

- **间隔间距刻度没有 100% 收敛。** 版式层面（区块、卡片、表格、抽屉、栅格）已经全部走
  `--space-*` 七档。但控件的光学内边距仍有 1–11px 的裸值（`.btn` / `.input` / `.badge` /
  `.segmented` 等约 20 处）：13px 的字配 8px 内边距显得虚胖、配 4px 又发紧，硬套 4 的刻度
  会让控件高矮不一。`app.css` 头部已把这条例外写明，不再是一条被默默违反的规则。
- **中间提交的树不是逐提交可运行。** `app.css` 是一个文件，三条改动线（设计系统 /
  页面 / 审核与轨迹）的样式都落在里面，按文件切分只能整体进第 1 个 commit。
  后果：只看第 1 个 commit 时，`app.css` 已删掉的两个工具类（`.clamp-2` / `.clamp-3`）
  还被那两份尚未提交的旧组件引用着——纯视觉差异，不报错。见 §9。

### P2 遗留

- 抽屉里的"研究素材"默认只展开 3 条，没有"展开全部"的统一控件（超出后需逐条展开）。
- 表格在 768px 以下靠横向滚动，没有做卡片式重排。做了的话会牺牲桌面端的效率，
  而这是运营控制台的主要使用场景。
- `TrendChart` 没有做数据点密度的自适应：窗口拉到 90 天时横轴刻度会变挤
  （`shortDate` 已经是短格式，暂够用）。

### 不在本次范围、但必须记下来的后端问题

**`GET /api/admin/analytics` 对所有窗口都返回 HTTP 500**，而其它 admin 接口都是 200。

- 复现：`curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8000/api/admin/analytics` → `500`；
  经 Vite 代理同样 500。响应体是纯文本 `Internal Server Error`（不是 JSON）。
- 根因（在进程内复现得到）：`pydantic_core.ValidationError: 1 validation error for TopicCount /
  topic — Input should be a valid string [input_value=None]`，抛在 `app/services/admin.py:569`。
  上游是 `app/repositories.py:820` 的 `topic_distribution()` 按 `AgentRun.topic` 分组时**包含了
  NULL 值**，而 Phase 5A 会给一个正在选题的 Agent Run 写入 NULL topic。
- 影响：在这个环境下数据分析页会显示它的错误态（"HTTP 500" + 一句安全文案 + 重试按钮），
  不会白屏、不会漏出 stack。
- 为什么没修：`app/**` 在本次的禁区里。**这是后端的问题，需要后端一行改动**
  （分组时过滤 NULL，或让 schema 允许 `topic: str | None`）。
